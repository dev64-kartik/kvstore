# Edge cases

Every failure scenario we've identified, how it's handled, and which test covers it.
Status: **planned** (designed, not yet built) · **handled** (code + test exist) · **known gap** (deliberately not handled).

## Phase 1 — single-node durability

| # | Scenario | Handling | Where | Test | Status |
|---|---|---|---|---|---|
| 1.1 | Crash mid-append: last record partially on disk (short header/payload) | Torn tail: scan stops at the last good offset; `Open` truncates there and syncs before any append | `wal.scanSegment`, `wal.openLast` | `TestScanTornTailAtEveryCut`, `TestOpenRepairsTornTail`, `TestCrashRecoverAppendCycles` | handled |
| 1.2 | Crash after the file size is persisted but before the data: zero/garbage-filled tail, or a full-length record with a zeroed sector | Bad record with no valid record after it → torn | `wal.scanSegment` | `TestScanTornTailShapes` | handled |
| 1.3 | Bit flip in a record mid-log | Forward scan finds the next valid record → `ErrCorrupt`, never skipped | `wal.scanSegment`, `findLaterRecord` | `TestScanMidLogDamageIsCorrupt` | handled |
| 1.4 | Bit flip in a *length* field mid-log, making real damage look like a torn tail | Forward scan finds the next valid record → `ErrCorrupt` | `wal.findLaterRecord` | `TestScanMidLogDamageIsCorrupt` ("length points past EOF") | handled |
| 1.5 | Corrupt length claims a huge payload | `length > MaxPayload` → `ErrBadRecord` (not `ErrTruncated`), checked before the length is used | `wal.DecodeRecord` | `TestDecodeOversizedLengthIsBadNotTruncated` | handled |
| 1.20 | Single bit flip anywhere in a record | CRC32C (guaranteed for crc/seq/payload; length flips change the checksummed range) | `wal.DecodeRecord` | `TestDecodeDetectsEveryBitFlip` | handled |
| 1.21 | Record cut short at any byte | `ErrTruncated` | `wal.DecodeRecord` | `TestDecodeTruncatedAtEveryLength` | handled |
| 1.22 | Valid CRC but malformed payload (writer bug) | Payload parsed strictly → `ErrBadRecord` | `wal.decodePayload` | `TestDecodeMalformedPayloadWithValidChecksum` | handled |
| 1.23 | Record that can't be read back gets written | Same limits checked on encode → `ErrInvalidRecord` | `wal.AppendRecord` | `TestAppendRecordRejectsInvalid`, `FuzzRecordRoundTrip` | handled |
| 1.25 | Failed open returns a non-nil `File` wrapping a nil `*os.File`, so `f != nil` checks pass and `Close` fails | `wrap` returns a literal nil on error | `vfs.wrap` | `vfstest` `MissingFileIsNotExist` | handled |
| 1.24 | Appending to a decoded key overwrites the next field | Decoded slices have capacity capped (`p[:n:n]`) | `wal.readLengthPrefixed` | `TestDecodeAliasesInput` | handled |
| 1.6 | Seq gap or regression (missing/reordered segment) | In a segment: checksum-valid record with the wrong seq → `ErrCorrupt`. Across segments: each must start where the previous ended → `ErrCorrupt` | `wal.scanSegment`, `wal.Open` | `TestScanSeqOutOfOrderIsCorrupt`, `TestOpenRejectsBrokenLayouts` | handled |
| 1.7 | Bad record in a sealed (non-last) segment | Always `ErrCorrupt` | `wal.scanSegment` | `TestScanTornTailAtEveryCut` (sealed case) | handled |
| 1.8 | Crash while creating a segment | `.tmp` + header + fsync + rename + dir fsync, so a visible name always has a complete header; `Open` removes leftover segment `.tmp` files (otherwise `O_EXCL` would block that segment forever) | `wal.CreateSegment`, `wal.removeTempSegments` | `TestCreateSegmentCrashAtEveryOp`, `TestOpenRemovesTempSegmentsAndIgnoresStrangers` | handled |
| 1.9 | New file's directory entry not persisted | Dir fsync after rename, before any record is acknowledged into the segment | `crashfs.FS.Crash` (simulation), `wal.CreateSegment` | `TestSyncedFileWithoutDirSyncVanishes`, `TestRenameAndRemoveNeedDirSync`, `TestCreateSegmentCrashAtEveryOp` | handled for segments; snapshots: step 6 |
| 1.26 | Crash simulator itself wrong: synced bytes changed by later unsynced writes (truncate then append) | `Sync` stores a separate copy | `crashfs` `file.Sync` | `TestDropUnsyncedRevertsTruncateAndOverwrite` | handled |
| 1.27 | Crash simulator not replayable: same seed, different outcome (Go map iteration order is random) | `Crash` walks directories and entries in sorted order | `crashfs.FS.Crash` | `TestCrashIsDeterministic` | handled |
| 1.10 | `Write`/`Sync` error on WAL | Writer permanently failed (`ErrFailed`), no retry; the DB remembers the failure, because rotation would otherwise swap in a healthy writer: every later write and snapshot returns `localdb.ErrFailed`, reads continue, the unacknowledged write is never visible; reopen restores writes | `wal.Writer.fail`, `localdb.DB.fail` | `TestIOErrorFailsWriterForever`, `TestWALFailureFailsWritesButNotReads`, `TestSnapshotAfterWALFailureIsRefused` | handled |
| 1.11 | Failed fsync leaves never-persisted bytes in page cache; same-OS reopen sees them | Not fully handled: shows up as `ErrCorrupt` after reboot; Phase 3 rebuilds from peers | — | — | known gap |
| 1.12 | Crash during snapshot before rename | Data synced before rename; leftover `.tmp` removed on load; recovery uses the previous snapshot plus all segments (none are deleted before the install) | `store.WriteSnapshot`, `store.LoadLatest`, `localdb.DB.Snapshot` | `TestWriteSnapshotCrashAtEveryOp`, `TestCrashDuringSnapshotAtEveryOp` | handled |
| 1.13 | Crash after snapshot rename, before or during cleanup | Replay skips `seq ≤ snapSeq` and doesn't read covered segments; the next `Snapshot` (even with nothing new) finishes the cleanup | `wal.Open`, `localdb.DB.collectGarbage` | `TestCrashDuringSnapshotAtEveryOp` (every op × both policies) | handled |
| 1.14 | Snapshot file corrupt (bit rot / bug) | CRC checked before any field is trusted, then strict parsing (key order, count, trailing bytes); no fallback | `store.decodeSnapshot` | `TestSnapshotDetectsEveryBitFlipAndTruncation`, `TestSnapshotMalformedWithValidChecksum`, `FuzzDecodeSnapshot` | handled |
| 1.15 | Caller mutates key/value buffer after `Put` / mutates value returned by `Get` | Store copies in and out | `store.Map.Put` / `Get` | `TestMapCopiesInAndOut` | handled |
| 1.18 | Write to the live map leaks into a snapshot clone (in-place update of shared storage) | `Put` always inserts fresh slices; btree copies shared nodes before writing | `store.Map.Put`, `google/btree` COW | `TestCloneIsolatedUnderConcurrentWrites`, clone checks in `TestMapMatchesModel` | handled |
| 1.19 | Empty value confused with missing key | A found value is always non-nil | `store.Map.Get`, `copyBytes` | `TestMapEmptyValueIsNotMissing` | handled |
| 1.16 | `ctx` cancelled while waiting for the writer | `select` on the slot and `ctx.Done()`; `ctx` re-checked after acquiring, because `select` picks randomly when both are ready, so a cancelled `ctx` never writes. Not honored once the WAL write starts | `localdb.DB.acquire` | `TestCancelledContextWritesNothing` (slot free × 100, slot held) | handled |
| 1.17 | Two processes open the same data dir | Not handled (no `flock`) | — | — | known gap |
| 1.28 | New segment created over a live one (stale startSeq), silently replacing acknowledged data via rename | Refuse if the name exists → `fs.ErrExist` | `wal.CreateSegment` | `TestCreateSegmentRefusesExisting` | handled |
| 1.29 | Acknowledged WAL record lost after power loss | One `Write` + `Sync` per record; ack only after `Sync` | `wal.Writer.Append` | `TestAckedAppendsSurviveCrash`, `TestCrashDuringAppendsKeepsAckedPrefix` | handled |
| 1.30 | Rejected (invalid) record poisons the writer or uses up a seq | Validation before any I/O; seq advanced only after `Sync` | `wal.Writer.Append` | `TestInvalidRecordDoesNotFailWriter` | handled |
| 1.31 | Torn in-flight record whose *value* contains a forged, checksum-valid record with the next seq: the forward scan finds it and reports corruption | Not handled: the DB refuses to start (loud, no data lost). The fix would be to skip over the bad record's declared length when it's plausible, which would weaken the defense in 1.4 | `wal.findLaterRecord` | — | known gap |
| 1.32 | Bad or short segment header in the last segment "repaired" as a torn write | The header is synced before the file is named, so a bad header is always `ErrCorrupt` | `wal.checkSegmentHeader` | `TestScanBadHeaderIsCorrupt` | handled |
| 1.33 | Log ends before the snapshot, or no segments at all while a snapshot exists | `ErrCorrupt`: appending would reuse seqs the snapshot already covers, or writes after the snapshot are missing | `wal.Open` | `TestOpenRejectsBrokenLayouts` | handled |
| 1.34 | Damage in a segment wholly covered by the snapshot (GC hadn't deleted it yet) | Not read at all, so it doesn't block startup | `wal.Open` | `TestOpenSkipsSegmentsCoveredBySnapshot` | handled |
| 1.35 | Crash during recovery itself (mid-truncate, mid-replay) | Recovery is repeatable: the next `Open` sees the same or an already-repaired tail | `wal.Open` | `TestCrashRecoverAppendCycles` | handled |
| 1.36 | A record recovered once disappears in a later recovery | After a crash everything visible is durable; the cycle test carries each recovery's result into the next | `wal.Open` | `TestCrashRecoverAppendCycles` | handled |
| 1.37 | Snapshot rotation when the current segment is still empty: `CreateSegment(lastSeq+1)` collides with the current segment's own name | Nothing new since the last snapshot → no file, cleanup only. Current segment empty (a retry after a failed attempt) → skip rotation, it already starts at `lastSeq+1` | `localdb.DB.cut` | `TestSnapshotWithNothingNewIsNoop`, `TestSnapshotRetryAfterFailure` | handled |
| 1.38 | Newest snapshot damaged while an older one is intact | `ErrCorrupt`, no silent fallback: the WAL bridging the older snapshot may already be deleted | `store.LoadLatest` | `TestLoadLatestDoesNotFallBack` | handled |
| 1.39 | Failed or cancelled snapshot leaves a `.tmp` that blocks the next attempt (`O_EXCL`) | Temp file removed on every failure before the rename | `store.WriteSnapshot` | `TestWriteSnapshotFailureCleansUp` | handled |
| 1.40 | Snapshot renamed or misplaced: file name seq ≠ header seq | `ErrCorrupt` | `store.LoadLatest` | `TestLoadLatestRejectsNameHeaderMismatch` | handled |
| 1.41 | Snapshot of a map that writers are still changing | `WriteSnapshot` reads only a `Clone` taken holding `writeSlot` + `mu`, in the same critical section that reads the seq | `localdb.DB.cut` | `TestCloneIsolatedUnderConcurrentWrites`, `TestSnapshotConcurrentWithWrites` | handled (seq/clone agreement itself isn't observable in final state: see 1.50) |
| 1.42 | A `Get` sees a write that a crash then erases | WAL `Append` (fsync) before the tree update; the tree holds only acknowledged writes | `localdb.DB.write` | `TestWALFailureFailsWritesButNotReads` (failed write never visible) | handled |
| 1.43 | Acknowledged `Put` not visible to a `Get` that starts after it returns | `Put` returns only after the tree update under `mu` (the linearization point) | `localdb.DB.write` | `TestConcurrentWritersAndReaders` | handled |
| 1.44 | Replay into the tree keeps pointers into the WAL read buffer | `Map.Put` copies key and value | `localdb.Open` replay, `store.Map.Put` | `TestMatchesModelAcrossReopensAndCrashes` | handled |
| 1.45 | `Close` while a write or snapshot is in flight closes the WAL under it / deletes files after Close | `Close` takes `snapSlot` then `writeSlot` (without `ctx`), so it waits for both | `localdb.DB.Close` | — (no deterministic test without a hook mid-op; see step 8) | handled, untested |
| 1.46 | WAL rotation fails after `CreateSegment`'s rename: the new segment's name exists while appends continue in the old one | Fail-stop (`ErrFailed`); otherwise the next `Open` sees the old segment run past the new one's start and refuses to start | `localdb.DB.rotate` | `TestRotationFailureFailsDB` | handled |
| 1.47 | Snapshot retried after an attempt that renamed the file but failed the dir sync: `WriteSnapshot` refuses the existing name | Accept it and sync the dir: it was synced before the rename, and the state at a seq is fixed by the log | `localdb.DB.Snapshot` | `TestSnapshotRetryWithNothingWrittenInBetween` | handled (its dir sync is masked by cleanup's; untested in isolation) |
| 1.48 | GC deletes a segment still needed (off by one at the boundary) | A segment is deleted only when the next one starts at or before `snapSeq+1`; the last segment is never deleted; GC runs only after the snapshot is installed | `wal.RemoveCovered`, `localdb.DB.Snapshot` | `TestRemoveCovered`, `TestCrashDuringSnapshotAtEveryOp` | handled |
| 1.49 | Failed snapshot blocks writes or poisons the DB | Only rotation failure fails the DB; file write, install and cleanup failures return an error and can be retried while writes continue | `localdb.DB.Snapshot` | `TestSnapshotRetryAfterFailure` | handled |
| 1.50 | Snapshot holds writes past its seq (clone taken outside the critical section that read the seq) | Prevented by taking both under `writeSlot`. **Not detectable by final state today**: replaying puts/deletes after the snapshot overwrites the extra ones identically. It becomes visible with CAS (Phase 3), whose outcome depends on the prior value | `localdb.DB.cut` | — | handled, untested |
| 1.51 | Any interleaving of ops, crash point (including inside recovery and snapshots) and crash policy loses an acknowledged write, resurrects an old one, or produces a state no prefix of the ops explains | Recovered state must equal durable state + every acknowledged op + at most the one in flight; the result is the next cycle's base | all of Phase 1 | `TestRandomCrashes` (100 seeds × 6 cycles, logs where crashes landed), `TestSIGKILL` (real process, real disk) | handled |
| 1.52 | Crash simulator more forgiving than real filesystems: crashfs keeps a *prefix* of unsynced directory ops, so a later op surviving implies every earlier one did. POSIX promises no such order. With the snapshot's dir sync removed, cleanup's later removals can't survive without the rename in crashfs, so `TestRandomCrashes` passes; on a filesystem that reorders, the old segments could be gone and the snapshot name too | Not modelled. The rule (dir sync after rename, before cleanup) is enforced by `TestWriteSnapshotCrashAtEveryOp`, which crashes right after the rename | `crashfs` `random.keepDirOps` | — | known gap (simulator fidelity) |
| 1.53 | `SIGKILL` can't detect missing fsyncs: the OS keeps the page cache across a process crash | By design: `TestSIGKILL` checks the real-OS code paths; power loss is covered by crashfs. Most kills also land between ops, since the child runs ahead of the parent's reads | `TestSIGKILL` | — | known gap (test scope) |

## Phase 2 — gRPC server and client

| # | Scenario | Handling | Where | Test | Status |
|---|---|---|---|---|---|
| 2.1 | Missing key reported as a failed request (counted by interceptors/metrics, confused with real errors) | `found = false` with status `OK`; the client maps it to `ErrNotFound` | `server.Server.Get`, `client.Client.Get` | `TestGetFoundAndEmptyValues`, `TestGetOutcomes` | handled |
| 2.2 | Empty value confused with a missing key on the wire (proto3 can't tell empty `bytes` from absent) | Explicit `found` field, never inferred from the value | `server.Server.Get`, `kv.proto` | `TestGetFoundAndEmptyValues` | handled |
| 2.3 | Client's deadline/cancel doesn't reach the store, so a write keeps waiting for the writer slot after the client gave up | Request `ctx` passed straight to the store | `server.Server.Put`/`Delete` | `TestClientContextReachesStore` | handled |
| 2.4 | Oversized request buffered in memory (gRPC default: 4 MiB) before the store rejects it | `MaxRecvMsgSize` = largest valid key + value + 4 KiB → `ResourceExhausted` before the handler runs | `server.Options` | `TestRequestSizeLimit` | handled |
| 2.5 | A store error mapped to a code that promises an outcome it can't (e.g. a WAL failure reported as "not applied") | Only `InvalidArgument` (and `ResourceExhausted`) say "not applied"; ctx errors keep their codes, `ErrFailed`/`ErrClosed` → `Unavailable`, unknown → `Internal` and logged | `server.Server.toStatus` | `TestErrorMapping` | handled |
| 2.6 | Client told a write failed when it may be durable (deadline mid-append, WAL failure, connection reset) | Only `InvalidArgument`/`ResourceExhausted` become `ErrInvalidArgument` ("not applied"); every other code, including ones we don't expect, becomes `ErrIndeterminate`, with the status still wrapped | `client.classify` | `TestWriteOutcomes`, `TestServerDownFailsFastAndIndeterminate` | handled |
| 2.7 | Empty value comes back as `nil` (proto3 decodes empty `bytes` as nil), so callers can't tell it from "missing" via `v == nil` | Client returns `[]byte{}` for a found empty value | `client.Client.Get` | `TestClientMatchesModelAcrossCrash` (always ends with an empty value) | handled |
| 2.8 | Caller's own cancel/deadline invisible to `errors.Is(err, context.Canceled)` (gRPC reports it as a status, which doesn't wrap the context error) | Client wraps `ctx.Err()` too | `client.classify` | `TestCancelledWriteIsIndeterminate` | handled |
| 2.9 | Acknowledged write over the network lost on power loss | Same rule as in-process: the server answers `OK` only after `localdb.Put` returned, i.e. after fsync | `server` → `localdb` | `TestClientMatchesModelAcrossCrash` (crashfs, read back through a new node) | handled |
| 2.10 | Client blocks indefinitely while the server is down | gRPC default fail-fast: the call returns `Unavailable` → `ErrIndeterminate` instead of waiting for a connection | `client.New` (defaults) | `TestServerDownFailsFastAndIndeterminate` | handled |
| 2.11 | Clients read a partially recovered state, or a node serves a dir it couldn't recover | Recovery (`localdb.Open`) runs before `net.Listen`; any recovery error exits with status 1 | `kvnode.run` | `TestUnrecoverableDirIsNeverServed` (corrupt snapshot, missing dir, missing `-dir`; never logs "listening") | handled |
| 2.12 | SIGTERM cuts off in-flight RPCs | `GracefulStop` drains them; after 10 s `Stop` cancels the rest (safe: a write's ctx is never honored mid-append) | `kvnode.gracefulStop` | `TestGracefulStopDrainsInFlightRPCs`, `TestGracefulStopCancelsAfterTimeout` | handled |
| 2.13 | DB closed while RPCs are still draining, so in-flight writes fail with `ErrClosed` | Order: drain RPCs → stop snapshot ticker → `db.Close` | `kvnode.run` | — (needs a write in flight exactly at SIGTERM) | handled, untested |
| 2.14 | Acknowledged write lost when the node process is killed; a write racing the kill half-applied | Same durability path as Phase 1; the in-flight write is either fully there or absent | `kvnode` end to end | `TestSIGKILLWhileWriting` (5 kill/restart rounds, snapshots every 1 ms, seeded) | handled (process crash only; power loss is crashfs's job, 1.53) |
| 2.15 | One failed snapshot stops all future snapshots, so the WAL grows forever | Logged, retried on the next tick | `kvnode.snapshotLoop` | `TestSnapshotLoop`; ticker wiring: `TestSIGTERMShutsDownCleanly` (waits for a snapshot file) | handled |
| 2.16 | Node reachable from the network with no TLS or auth | Default `-addr 127.0.0.1:7070` | `kvnode` flags | — | handled by default; known gap if overridden |
